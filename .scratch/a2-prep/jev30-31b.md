# Prep for wave A2 — from JEV-30 / JEV-31b (the config-staleness family)

Written for JEV-32 first (it is this family seen from the analysis side), then
JEV-49, JEV-16, JEV-43. Every line/number here was checked against the tree at
the commit that closed JEV-30/31b.

---

## 1. The one-sentence model

A row carries **two kinds** of config-derived value, and they behave
oppositely:

* **Stamped** — resolved at *write* time by the process that produced the row,
  and frozen into the row. Safe to trust. Never re-derivable.
* **Resolved at read time** — `analyze.py` calls `config_loader` *now*, against
  rows written days ago under a config that may differ. This is JEV-32.

Until this wave, the only stamped config identity was `pricing_version` and
`question_set_id`, both of which are **hand-maintained strings**. That is the
hole: an operator can edit a *rate* without bumping `pricing.json:version`, and
two rows then carry the same `pricing-2026-09-20` over different numbers.
`config_loader.config_fingerprint()` now exists to close it — see §4.

## 3. Resolved at READ time — this is JEV-32's whole problem

| site | call | hazard |
|---|---|---|
| `src/analyze.py:264` | `cl.question_set(surface)` | takes the **current** pin; rows carry the pin they ran under |
| `src/analyze.py:339` | `cl.question_set(surface)` | same |
| `src/analyze.py:325` | `cl.pricing()['version']` | prints today's pricing version in a report over rows stamped with possibly another |
| `src/validate_threshold.py:135,151` | `cl.question_set_id(surface)` then filter `r["question_set_id"] != primary_qsid` | already does the right thing: **filters** rather than pools. Copy this shape |
| `src/determinism.py:140,170,177` | same pattern, keys repeat-groups on `question_set_id` | also already correct |

**So `analyze.py` is the outlier, not the rule.** `validate_threshold.py` and
`determinism.py` already treat `question_set_id` as a row-level key and compare
against the configured one. JEV-32 is mostly "make `analyze.py` do what its two
siblings already do", which is a much smaller and much more defensible change
to a frozen file.

### What JEV-32 has to do to join rows to the config that produced them

1. **Group, never pool.** Partition rows by `question_set_id` before any
   statistic. Pooling `pre_bash/v1#a` with `pre_bash/v1#b` is already wrong
   (different phrasing = different row by design, CONTEXT.md).
2. **Assert, then report.** For each group, assert the spec applied is the spec
   named by the row, and fail loudly on mismatch. Today all 2,005 rows carry
   `pre_bash/v1#a`, so the pre-/post-fix numbers PREREGISTRATION §8 demands
   should be **identical** — say so explicitly; that is the cheapest possible
   discharge of the freeze obligation.
3. **The arm set has no row-level version at all.** `arm_order` is the only
   trace. JEV-32 must either bisect on `evaluated_at` against the 12:07:24Z
   restart (ISSUES.md JEV-30, "Boundary recorded") or — better — key on
   `len(row["arm_order"])` / `set(row["arm_order"])`, which is intrinsic to the
   row and needs no external timestamp. **Prefer the intrinsic key**: JEV-43 is
   about wall-clock contamination, and bisecting a dataset on a wall clock is
   the same smell.
4. **`cost_usd` cannot be recomputed from `pricing_version` alone.** See §4.
5. **Rows written before the fingerprint lands have no fingerprint.** Treat its
   absence as "the pre-fingerprint era", the same convention `arm_dispatch`
   already uses (`src/worker.py:241-243`).

## 4. `config_fingerprint()` — what it is and why

`src/config_loader.py`, `config_fingerprint()`. Returns:

```json
{"config_sha256": "ea4a16c176e233fa",
 "files": {"surfaces.json": "eaec50ffd523", "arms.json": "4e1a55241457",
           "pricing.json": "5d69c2f131c5"},
 "surfaces_version": "surfaces-v1", "arms_version": "arms-v1",
 "pricing_version": "pricing-2026-09-20"}
```

`config_sha256` is derived from the **bytes** of all three config files. Two
rows with the same value were produced under byte-identical config; two rows
that differ were not, whatever their version strings say. The version strings
are the readable half and are kept, but they are hand-maintained and therefore
not trustworthy as a join key — that is the entire argument.

It is **not yet stamped on any row**: `worker.py`, `replay.py`, `canary.py` and
`baseline.py` are not owned by this ticket. See §6.

Scope note: question-set files are deliberately **not** in the fingerprint.
They are frozen by PREREGISTRATION §8 and every row already carries
`question_set_id`.

## 5. Staleness semantics, per writer — a real finding for JEV-16 and JEV-32

The two live writing paths have **opposite** staleness behaviour, and this is
not documented anywhere else:

| writer | config read | mid-window edit |
|---|---|---|
| `src/worker.py` (spool drain) | once per process, `functools.cache` | **never** picked up until restart — was silent, now raises `ConfigStaleError` |
| `hooks/inline_shadow_bash.sh` (`:81,120,296`) | jq, **every hook fire** | picked up **immediately**, silently |

So a mid-window edit to `surfaces.json` flips inline-shadow rows at once and
worker rows never. If JEV-16's determinism sweep or JEV-35's inline surface
ever runs alongside the worker, the two row streams can disagree about the
question-set pin **within the same wall-clock second**. `run_context` does not
separate them — both write `live`. Recommend JEV-16 check this explicitly.

`hooks/capture.sh` reads no config at all except the kill-switch `[ -e ]` test
(by design: fork-free, <10ms).

## 7. For JEV-49 (cost pipeline)

* `cost_usd` and `pricing_version` come from **one cached blob**
  (`config_loader._pricing()`), so within a process they are always consistent.
  The Console-reconciliation gap is therefore **not** a stale-cache artefact —
  look elsewhere.
* The known modelling gaps are documented in `config/pricing.json` itself and
  are the likely reconciliation deltas: `claude-opus-5[1m]` is billed per
  request above a threshold but priced flat (`blended_observed_input` 5.199e-06
  vs `input` 5e-06); `claude-fable-5-1`'s `cache_read_multiplier: 0.025` is
  **unverified** against cost-state.
* `web_search_usd_per_request` is consumed only in `src/session_metrics.py:261`
  — not in `cl.cost_usd()`. Per-call run rows therefore **exclude web search**;
  session baselines include it. Do not reconcile the two without accounting for
  that.
* `pricing.json:as_of` has no consumer and is allow-listed as documentation in
  the key-sweep test.
