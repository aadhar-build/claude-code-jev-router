## 0. What changed under you this wave

`src/worker.py` gained ~200 lines at the top (the lifecycle note + the claim /
reap / signal helpers) and `drain_once` gained a kill-switch check. **Every
line number in `worker.py` from earlier prep notes is now wrong.** The
row-writing block did not move relative to `process_capture`, but its absolute
position did.

Three behavioural changes that can affect a measurement:

1. `drain_once` returns 0 immediately when `.jev-disabled` is present. It reads
   the switch at the top of the cycle **and before every claim**.
2. A claimed file is now named
   `{base}__p{worker_pid}__t{claim_epoch}__r{retries}.json`. Anything that
   parses a spool filename beyond `split("__", 1)[0]` will need the regexes in
   `worker._CLAIM_RE` / `worker._READY_RETRY_RE`.
3. `worker.main()` calls `reap_claimed()` once at startup. A reaped capture
   comes back as `{base}__r{n}.json` and is **re-evaluated from scratch** — new
   `decision_id`, same `state_sha256`. See §5, it matters for JEV-32/49.

`worker.py` also now uses `paths.SPOOL_CLAIMED` / `paths.SPOOL_DEAD` instead of
re-deriving `paths.SPOOL / "claimed"`. Identical in the live tree; **not**
identical under the old `test_pipeline.TempStorage`, which is why that fixture
was fixed too.

## 1. The shape of a run row — where each field is set

Two streams, joined on `decision_id`.

**Capture row** — `worker.process_capture`, the dict literal at
`src/worker.py:426-446`, written by `store.append_capture` at :463. One per
decision point. Carries `state_sha256`, `state_chars`,
`state_builder_version`, `state_source`, `run_context`, `picked_at`, plus the
session/prompt/tool identifiers off the hook payload.

**Run row** — one per (decision point × classifier arm). Built at
`src/worker.py:468-489` as `run.to_dict()` (from `arms/base.Run`) then
`row.update({...})`. The fields the worker adds on top of the arm's own:

| field | set at | note |
|---|---|---|
| `decision_id`, `surface`, `session_id`, `state_sha256`, `run_context` | :470-475 | join keys; copied from the capture |
| `question_set_id` | :473 | **resolved once** at :414 and passed to both the questions actually asked and the id recorded, so they cannot drift |
| `arm_dispatch` | :479 | `"concurrent"`. **Absent** on pre-2026-09-20 rows and absence *means* sequential. The era marker — condition on it |
| `arm_order`, `arm_order_position` | :480-481 | post-boundary these are **submission** order, not execution order. No longer a latency-confound control |
| `concurrent_arms` | :482 | how many arms were in flight together |
| `dispatch_offset_ms` | :483 | ms from the decision's t0 to when *this* arm's call began |
| `dispatch_wall_ms` | :484 | t0 to the last arm finishing, per decision |
| `evaluated_at` | :485 | `store.utcnow()`, written **after** the dispatch returns |
| `pricing_version` | :486 | `cl.pricing()["version"]` — **current config at write time** |
| `config_fingerprint` | :487 (and :446 on the capture row); resolved ONCE at :424 | **new this wave (JEV-30).** `cl.config_fingerprint()['config_sha256']` — the identity of the config, derived from the BYTES of `arms.json` + `surfaces.json` + `pricing.json`, not from a version string. Also on the **capture** row. This is the join key JEV-32 actually wants |
| `cost_usd` | :488 | `cl.cost_usd(...)` — **current config at write time**, `None` when `not run.ok` |

`replay.py` and `canary.py` write rows through their own paths and **omit**
`arm_dispatch` / `dispatch_*` / `concurrent_arms`; they are sequential.

### `arm_config_id` — the flow, for JEV-43 and JEV-16

```
config/arms.json  →  cl.arm(name)  →  ArmConfig.arm_config_id
                  →  Run(arm_config_id=...)        arms/*.py, and worker.py:354
                                                   on the failure path
                  →  run.to_dict()                 arms/base.Run
                  →  the row, unchanged
```

It is **never** recomputed at analysis time, which makes it the only reliable
era key on a row. `cc_haiku45` rows split `cc-haiku45-cli-v1` (thinking not
suppressed) from `cc-haiku45-cli-v2-nothink`, and their cost and latency **do
not pool**. `arm` alone is not sufficient to group by — JEV-43 and JEV-16 both
need `(arm, arm_config_id)`, and JEV-16 additionally needs `arm_dispatch`.

The failure path at `worker.py:345-359` is worth knowing: an arm that raises
still produces a row, with `ok=False`, the correct `arm` and `arm_config_id`,
**no usage, no timing and `cost_usd=None`**. Attrition is rows, not gaps. Any
latency or cost aggregate must filter `ok` explicitly or it silently averages
over `None`.

## 2. Timing: what is recorded, and what it does and does not include

Three clocks, none of them measuring the same thing. **JEV-43 needs all three.**

1. **`timing_ms.total_ms`** — the arm's own `Clock`, started inside
   `arms/<kind>.evaluate`. For `claude_cli` this brackets the **whole
   subprocess**: spawn, Claude Code's ~5.2K-token preamble, the tool round
   trip, the model call, teardown. For `jev` it brackets one HTTP request.
   These are not comparable quantities and the report says so.
2. **`raw.duration_api_ms`** — for the `cc_*` arms, the API's own duration as
   Claude Code reports it. **This is the one that excludes spawn.**
   `total_ms - duration_api_ms` is the harness overhead, and it is where the
   operator's user-level hooks land.
3. **`dispatch_offset_ms` / `dispatch_wall_ms`** — measured in `_dispatch`
   (`src/worker.py:361-391`) off one `time.perf_counter()` t0 per decision.
   `offsets[position]` is written *inside* the pool callable, so it measures
   submission-to-start, i.e. thread-pool scheduling, not queueing behind
   another arm.

**What NO field includes:** the time a capture spent sitting in `spool/ready/`.
`picked_at` is stamped when `process_capture` begins, not when the hook wrote
the file, and the spool filename carries no timestamp. **Queue latency is
unrecoverable from the rows.** If JEV-43 wants end-to-end "decision to answer",
it does not exist; if it wants "how long did the arm take", it is above.

### The drain-loop biases a latency number must condition on

- **Concurrency contention (the big one).** Since JEV-33 all enabled arms are
  dispatched into a `ThreadPoolExecutor` together (`worker.py:387-389`).
  Concurrent `claude -p` spawns contend for CPU, so a `cc_*` arm's `total_ms`
  is inflated relative to the sequential era by an amount `concurrent_arms`
  lets you condition on. **Do not pool `total_ms` across `arm_dispatch`.**
  `raw.duration_api_ms` is far less affected and is the better cross-era
  quantity.
- **Results are collected in submission order** (`[f.result() for f in
  pending]`, :389), not `as_completed`. That does not change any recorded
  number — each arm's timing is taken inside its own callable — but it does
  mean `dispatch_wall_ms` is the max, not the sum.
- **The kill switch is checked before every claim** (new). It is a `stat` on a
  path, per capture, on the main thread, outside `_dispatch`'s t0. It cannot
  enter any recorded latency.
- **`spool_watch.sample()` runs on every claim** (:552), before the rename. It
  reads and rewrites a small JSON file. Also outside t0.
- **A reaped capture is re-evaluated from scratch**, so its latency is a fresh
  measurement of the same state — not a resumption. Fine for latency, **not**
  fine for anything that counts decision points; see §5.

## 3. JEV-49 specifically — where cost is computed

`cost_usd` is computed **once, at row-write time**, from `cl.cost_usd(model,
usage)` using whatever `config/pricing.json` said at that moment
(`worker.py:488`). It is a stored number, not a derived one. Two consequences:

- A pricing correction does **not** retroactively fix stored rows. Any
  reconciliation against the Console must either recompute from
  `usage` + `pricing_version` or state that it is comparing stored numbers.
- `pricing_version` is the only provenance on the row. An operator who edits a
  **rate** without bumping the version string produces two processes stamping
  the same version over different numbers — the JEV-30/31b agent's commit
  (`7ded9be`) added startup logging for exactly this; read it before assuming
  a version string is trustworthy for the whole window.
- `cost_usd` is `None` on every `ok=False` row. A sum that treats `None` as 0
  is right; a mean that skips them is measuring something else.

`cl.pricing()` is `@functools.cache`d — see §6.

## 4. JEV-32 specifically

The exposure is `worker.py:414` versus analysis time. The **worker** resolves
`version = version or cl.surface_question_version(surface)` once and derives
both the questions asked and the `question_set_id` recorded from that single
value, so a *row* is internally consistent by construction. `analyze.py`
resolves the spec from **current** config and applies it to rows carrying
whatever id they were run under. The row already carries the right answer —
`question_set_id`, e.g. `pre_bash/v1#a`. Nothing needs to be recovered; it needs
to be *read* and asserted.

Note the row's copy carries the `#<phrasing>` suffix and the config's does not
(`CONTEXT.md`). Compare on the `<surface>/<version>` part or the assertion will
fail on every row.

## 5. The landmine I introduced, and the one I did not

**Introduced, deliberately, and named on the board.** The startup reap can in
principle race a live claim, producing **two full sets of well-formed run rows
under two `decision_id`s sharing one `state_sha256`**. That is *inflation*, not
attrition. It is invisible to the PREREGISTRATION §5 assertion — the duplicates
are legitimately identical, so the same-state check passes — and it makes the
clustered bootstrap count one decision point as two, quietly falsifying its
independence assumption. Mitigated by never reaping a live pid at any age and
by reaping at startup only. **Anyone doing a count-based analysis should assert
`state_sha256` is unique per `run_context='live'` decision point and report any
collision rather than pooling it.** Today: zero collisions, because the reap has
never yet run against a real stranded file.

**Not introduced but present:** `data/runs/` has no uniqueness constraint of
any kind. `store.append_run` appends. Any re-run, replay or reap duplicates.

## 6. Landmines I hit, concretely

1. **`.jev-disabled` is PRESENT for all of Phase A, and `paths.killed()` reads
   `paths.KILL_SWITCH` at call time.** `tests/test_pipeline.py:TempStorage` did
   not repoint it; `tests/gate4_drain.py:repoint` does. Any new test that
   drains **must** repoint `KILL_SWITCH` into its sandbox *and* carry a control
   with the switch absent, or it passes vacuously. Fixed in `TempStorage` this
   wave — but check any fixture you write yourself.
2. **`functools.cache` on `cl.surfaces()`, `cl.pricing()`, `cl.question_set()`**
   (`src/config_loader.py`). If you repoint `paths.CONFIG` in a test you must
   `cache_clear()` or you get the real config. I avoided this entirely by using
   the real read-only `config/` and only sandboxing writable paths —
   recommended, and `config/surfaces.json` has `pre_bash.mode: "shadow"`, so a
   drain against the real config does dispatch.
3. **`paths.ROOT` is computed from `__file__` and cannot be overridden by an
   environment variable.** A subprocess test of the worker needs a driver that
   imports `paths`, mutates the module attributes, and only then imports
   `worker`. `tests/worker_driver.py` is that driver; copy it rather than
   re-deriving it.
4. **PEP 475.** `time.sleep()` **resumes** after a signal handler that returns
   without raising, so a flag-setting handler plus `time.sleep(30)` gives you a
   worker that takes up to 30s to notice. Use `Event.wait(...)`, which returns
   True on set.
5. **`tests/test_python_floor.py` (JEV-44, landed mid-wave) enumerates
   `tests/test_*.py`** and requires both a PEP-723 `requires-python` header and
   a runtime `pyversion.require()` call. A new test module without them fails
   the suite. Files not matching `test_*.py` (like `worker_driver.py`) are
   exempt.
6. **`tests/audit_live_writes.sh` keys on the literal `$ROOT/(spool|data|logs)`
   and `$ROOT/.jev-disabled`.** Do not name a sandbox variable `ROOT` in a
   shell test — it would hide a real violation from the scanner. Use anything
   else; `tests/test_collection_control.sh` uses `SBX`.
7. **Four agents share one working tree.** `git status` shows other agents'
   uncommitted files continuously. Stage by explicit path, always. `ISSUES.md`
   in particular goes clean and dirty underneath you.

### Routed elsewhere — the config agent's handoff I could NOT complete

The JEV-30/31b agent asked for `"config_fingerprint": cl.config_fingerprint()
["config_sha256"]` on the row written by **`src/replay.py`** (~:87) and
**`src/canary.py`** (~:288), and for **`src/paths.py:82`'s `SURFACES` tuple to
be deleted** in favour of `cl.surface_names()`. I own none of those three
files and did not touch them.

`config_fingerprint` is resolved **once** per capture at `worker.py:424`,
beside the question version and **before** `_dispatch`. That placement is
load-bearing: `cl.config_fingerprint()` calls `assert_config_fresh()`, so
reading it per row would let a config edit landing during a dispatch raise
inside the row-writing loop, be swallowed by `drain_once`'s
`except Exception`, and quarantine a perfectly good capture to `dead/` **after
every arm call had already been paid for**. Asserted by
`test_the_config_fingerprint_is_resolved_once_before_dispatch`.

**This matters for JEV-16 directly.** `replay.py` is the determinism sweep's
entry point. Until that line lands, replay rows carry no `config_fingerprint`
while live rows do, so the two streams **do not join on it** — a sweep run
before the fix is not attributable to a config state. Add it before spending
the 90 calls, or state the gap in the sweep's report.

so the interpreter it resolved was bound for the whole window.

so JEV-37's cron wrapper has the same constraint — use the two-liner there
